# @hoshinotatsuya/deps-guard

[![npm](https://img.shields.io/npm/v/@hoshinotatsuya/deps-guard.svg)](https://www.npmjs.com/package/@hoshinotatsuya/deps-guard)
[![CI](https://github.com/HoshinoTatsuya/deps-guard/actions/workflows/ci.yml/badge.svg)](https://github.com/HoshinoTatsuya/deps-guard/actions/workflows/ci.yml)

[English](README.md) · [Changelog](CHANGELOG.md)

Гейт цепочки поставок npm-зависимостей для CI и хука коммита. Защищает **вход** зависимости в репозиторий: новая зависимость, новый install-скрипт, новый источник пакета или подозрительное имя не проходят без явного решения с причиной.

**От вредоносной зависимости в рантайме библиотека не защищает.** Пакет, прошедший гейт (с причиной, из разрешённого реестра, не свежий), исполняется в процессе с полными правами — гейт лишь не даёт ему попасть в дерево незамеченным. Изоляция процесса, запрет сети и права файловой системы — задачи окружения, а не этого пакета.

## Установка

```bash
pnpm add -D @hoshinotatsuya/deps-guard
# по необходимости, для гейта в jest:
pnpm add -D @jest/globals
```

Node.js **24 и новее**. Зависимостей рантайма нет; единственный (необязательный) peer — `@jest/globals >= 29` для подпути `./jest`.

## Быстрый старт

**1.** `deps-guard.json` в корне проекта (без него — отказ: значения по умолчанию судили бы чужой репозиторий чужими реестрами; неизвестный ключ — тоже отказ, опечатка не выключит правило молча):

```json
{
  "newDependencies": {
    "baseline": { "gitRef": "origin/main" },
    "allow": { "date-fns": "date parsing in reports instead of hand-written code" }
  },
  "installScripts": {
    "allow": { "esbuild": "downloads the binary for its platform; the build needs it" }
  },
  "sources": {
    "registries": ["https://registry.npmjs.org/"],
    "defaultRegistry": "https://registry.npmjs.org/",
    "allow": {}
  },
  "typosquatting": { "allow": {} },
  "freshness": { "minAgeDays": 7, "metadataFile": "deps-guard.metadata.json", "allow": {} },
  "floatingRanges": { "fields": ["devDependencies"], "allow": {} },
  "bannedPackages": [
    { "name": "request", "reason": "deprecated by its author; use the built-in fetch instead" }
  ]
}
```

**2.** Один раз выгрузить кэш метаданных реестра (даты публикации и признак install-скрипта ровно тех версий, что в lock-файле) и закоммитить — сама проверка дальше идёт без сети:

```bash
pnpm exec deps-guard metadata --out deps-guard.metadata.json
git add deps-guard.json deps-guard.metadata.json
```

**3.** Проверка:

```bash
pnpm exec deps-guard check --base origin/main
```

Код `0` — чисто, `1` — нарушения или устаревшие допуски, `2` — что-то не проверено или не прочитано (и нарушений нет).

**4.** В CI — **до** любого install-скрипта (см. [CI](#ci)) или в наборе тестов (см. [Гейт в jest](#гейт-в-jest)).

Настройка выше — [`examples/deps-guard.json`](examples/deps-guard.json), её проверяет разбор настройки самого пакета в его тестах; блоки TypeScript — файлы из [`examples/`](examples), их проверяет `pnpm run typecheck` против исходников пакета.

## Допуски

Каждая запись допуска — `предмет → причина` не короче 30 видимых знаков: считаются графемы (эмодзи, в том числе склеенные ZWJ-последовательности, и буква с ударением — один знак), в которых есть буква, цифра, знак препинания или символ; пробелы (и в середине), символы нулевой ширины, управляющие и «пустые» заполнители (U+115F, U+1160, U+3164, U+FFA0, U+2800) не считаются. Короче — нарушение, и допуском запись не считается. Запись, которой больше ничего не соответствует, — «устарело»: список допусков не растёт бесконечно. Правило отключается только с причиной: `"disabled": { "freshness": "…" }`; чтение входов (`input`) не отключается — такой ключ отказ, а не тишина.

## Правила

Каждая находка — правило, вердикт, путь (со строкой, где известна), предмет и причина.

| правило | что проверяет | настройка |
|---|---|---|
| `new-dependency` | Прямая зависимость, которой нет в базе, — только с записью в `newDependencies.allow`. Зависимость — настоящий пакет и его источник: пакет реестра — его имя (`npm:`-алиас, протокол без учёта регистра, — имя цели: `aa-lib: NPM:bb-lib@1.0.0` — новая зависимость `bb-lib`); пакет не из реестра — `имя@источник` (git — адрес без коммита, архив — адрес, каталог — путь от корня, ссылка — цель): смена источника под старым ключом (`aa-lib: https://…/bb-lib-1.0.0.tgz`, `aa-lib: evil/repo`) — новая зависимость `aa-lib@<источник>`, допуск пишется под этим предметом; смена коммита git — та же зависимость; config-зависимости pnpm (`configDependencies` — их код pnpm исполняет до установки) — тоже прямые. База — git-ревизия (`gitRef` или `--base`) или файл базовой линии (`file`, пишет `deps-guard baseline`). База считается по всему репозиторию: проекты базы — проекты её lock-файла и каталоги по её шаблонам workspace, поэтому перенос зависимости между пакетами и переименование пакета новым кодом не являются. Допуск удалённой зависимости — «устарело» | `newDependencies` |
| `install-script` | Пакет дерева с `preinstall`/`install`/`postinstall` (или `binding.gyp`), включая пакеты из `bundleDependencies`, обязан иметь решение: разрешён (`installScripts.allow` или решение менеджера) или явно запрещён. Решение засчитывается, только если его читает менеджер этой версии (см. таблицу ниже); заданный, но не читаемый ключ называется в находке. Плюс сверка, что настройка менеджера **действительно запрещает остальные**: pnpm 10+ — по умолчанию; pnpm < 10 — только при `onlyBuiltDependencies`; `dangerouslyAllowAllBuilds` — нарушение; версия pnpm не зафиксирована (`packageManager` или `devEngines.packageManager`) — нарушение. npm и yarn списков не знают: запрет подтверждается `ignore-scripts` (npm — `.npmrc`, yarn — `.yarnrc`) или `installScripts.othersBlockedBy`, иначе «не проверено». Заглушка pnpm 11+ `allowBuilds: { dep: set this to true or false }` (и любая строка вместо `true`/`false`) — решения нет: пакет со скриптом — нарушение. pnpm 12.11+: `permissions.<пакет>.build: true|false` — тоже решение и перекрывает `allowBuilds` того же ключа. Пакеты `packageManagerDependencies` (сам pnpm из `packageManager` и его сборки) решения не требуют: их ставит самоустановка pnpm, к ней `allowBuilds` проекта не применяется, а скрипты самого pnpm она не выполняет (замер). yarn 2+: без `enableScripts` запрет остальных — умолчание yarn 4.14+ (yarn.lock формата 9+); prepack git-зависимости yarn выполняет при любых настройках — только `installScripts.allow`. У git-зависимости и локального каталога install-скрипт — ещё и `prepare` (менеджер собирает их при установке); git-зависимость скрипт имеет всегда | `installScripts`, настройки менеджера |
| `source` | Каждый пакет — из разрешённого реестра (схема без учёта регистра, хост — без точки в конце, порт и префикс пути; `registry.npmjs.org.evil.example`, адрес с учёткой и путь с закодированным `/` или `\` не проходят) и с integrity, в котором есть хотя бы один корректный токен sha256/384/512 (base64 ровно длины хэша: `sha512-` без хэша или с обрезанным хэшем менеджер отбрасывает и не сверяет архив). git (в том числе `ssh://` и `git@хост:`), `file:`, каталог, http вне реестра, ссылка за пределы репозитория (в том числе абсолютная `link:/…`), нераспознанная запись — нарушение без записи `sources.allow["имя@источник"]` (git — адрес без коммита, архив — адрес без учётки, каталог — `file:путь`, ссылка — `link:цель`; находка называет точный ключ): допуск по одному имени пропустил бы под тем же именем любой адрес; git — ещё и только с коммитом. Допуск источника integrity не отменяет. Пакет из `bundleDependencies` судится вместе с родителем. Пакет без адреса в lock-файле (так pnpm v9 пишет реестр по умолчанию) ставится из реестра установки: `registry`/`@scope:registry` в `.npmrc` проекта (у yarn ещё `.yarnrc`) — такой реестр вне `sources.registries` нарушение, из переменной окружения — «не проверено»; если в проекте не задан — судится по `sources.defaultRegistry`, без неё — «не проверено» | `sources` |
| `typosquatting` | Имя каждого пакета дерева и прямой зависимости не похоже на популярное: смешение `-`/`_`/`.` и регистра (`cross_env`), перестановка частей (`env-cross`), подмена scope (`@types-x/node`, `@typess/node`), расстояние правки с перестановкой соседних букв (`lodahs`; порог 1 для имён 5–9 знаков, 2 — от 10, короткие не судятся). Список — `data/popular-packages.json` пакета или свой (`popularFile`, формат `{ "names": [...] }`); пустой — отказ | `typosquatting` |
| `freshness` | Версия из реестра опубликована не позже `minAgeDays` (по умолчанию 7) дней назад. Дата — из кэша метаданных в репозитории (`metadataFile`) или от вызывающего. Нет даты — «не проверено», дата в будущем — нарушение. Допуск — `имя@версия`; когда версия созрела, допуск больше не нужен — вердикт `matured` (предупреждение, код выхода не меняет: версия созревает сама, без коммита, и красный main на законном состоянии отключили бы); допуск версии, которой нет в lock-файле, — «устарело» | `freshness` |
| `floating-range` | Прямые зависимости проверяемых полей без запрещённых видов: `caret` (`^`), `tilde` (`~`), `x-range` (`1.x`), `any` (`*`), `tag` (`latest`), `comparator` (`>=`, `\|\|`). По умолчанию запрещены все виды во всех трёх полях; библиотеке обычно нужно `"fields": ["devDependencies"]`. У `npm:` и `jsr:` судится диапазон цели, у `catalog:` — диапазон из каталога pnpm-workspace.yaml (записи нет — не разобран). Пути (`./x`, `/abs`, `~/x`, `C:\x`), `workspace:`, `file:`, git в любой записи (`git+…`, `ssh://`, `git@хост:`, `владелец/репозиторий`), адреса — не диапазоны (тот же разбор, что у правила источников): их судит `source`. Неразобранный спецификатор — нарушение всегда | `floatingRanges` |
| `banned-package` | В установленном дереве нет пакетов из перечня `bannedPackages` (`[{ "name", "reason" }]`): ни прямых, ни транзитивных, ни поставленных менеджером peer (pnpm и npm 7+ ставят обязательный peer сами, yarn — нет), ни optional (в том числе других платформ — они записаны в lock-файле), ни под алиасом — судится настоящее имя пакета (`"db": "npm:x@^1"` и `x@npm:x@…` транзитивно — пакет `x`; ключ `"x": "npm:y@1"` — пакет `y`, не `x`). Дерево — по lock-файлу любого поддерживаемого формата (pnpm 6/9, npm 2/3, yarn 1, yarn 2+), установленный `node_modules` не читается. Peer, который объявлен и не установлен (необязательный, или у yarn), в дереве не стоит и нарушением не является. Находка — пакет `имя@версия` со строкой lock-файла, причина из перечня и цепочки от прямых зависимостей проектов: `package.json devDependencies.kit: kit@1.0.0 → orm-adapter@1.0.0 → x@1.0.0` (кратчайшая от каждой прямой зависимости, к которой пакет достижим, первые пять, остальные — числом); пакет, к которому не ведёт ни одна прямая зависимость, — нарушение с пометкой «запись без владельца». Нет ключа или пустой перечень — правило ничего не запрещает (это решение проекта, а не контроль доступа). Запись без причины (короче 30 видимых знаков), с именем не пакета реестра (с версией, диапазоном, пустое, путь, `@scope` без имени, заглавные в scope, длиннее 214 знаков), с лишним ключом и повтор имени — отказ настройки | `bannedPackages` |
| `lock-mismatch` | package.json и lock-файл согласованы: каждый проект workspace есть в lock-файле, каждая прямая зависимость записана с тем же спецификатором и в том же поле, лишних нет, и каждая записанная указывает на пакет, который в lock-файле есть (иначе дерево не проверено ни одним правилом). Согласованным считается то, что менеджер законно пишет иначе: спецификатор из `overrides` lock-файла pnpm, ссылки `link:` при `excludeLinksFromLockfile`, зависимость в двух полях package.json (менеджер пишет одно), у yarn 1 — зависимость на пакет workspace (её в yarn.lock нет; совпадение диапазона с версией пакета проверяет сам yarn при `--frozen-lockfile`). Config-зависимости pnpm-workspace.yaml и lock-файла совпадают; диапазон каждой используемой записи каталога pnpm (`catalog:[имя]`) совпадает с `catalogs.<имя>` lock-файла (каталог изменён без переустановки — `--frozen-lockfile` откажет) | — |

## Вердикты и коды выхода

| вердикт | значение | код |
|---|---|---|
| `violation` | нарушение правила | 1 |
| `stale` | допуск, которому ничего не соответствует | 1 |
| `unverified` | не проверено: нет данных (даты, признака скрипта, базы) | 2, если нет нарушений |
| `broken` | вход не прочитан: битый lock-файл, настройка, база | 2, если нет нарушений |
| `matured` | допуск свежести больше не нужен: версия созрела (удалите запись) | 0 — предупреждение; в тексте — строкой «созрело допусков N», в SARIF — `level: note`, в JUnit — `<system-out>` |

«Не смог разобрать lock-файл» — отказ с номером строки, а не пропуск. Разборщик YAML читает то, что пишет pnpm (и prettier поверх него): блочные скаляры `|`/`>` с индикаторами (многострочный `deprecated`), явный ключ `? …`/`: …` (ключ длиннее 1024 знаков), многострочные flow-коллекции (закрывающая скобка — и на отступе родителя), документ целиком в записи JSON. Прочитанное обязано совпадать с тем, как читают ОБА разборщика менеджеров: js-yaml (pnpm до 11) и собственный разборщик pnpm 12 (он читает скаляр по типу поля: в булевом `yes` — true, в строковом `True` — строка). Всё, что хоть один из них читает иначе, — отказ: якоря, теги, ключ слияния `<<`, одиночный CR, NEL, C1 и разделители строк Unicode, BOM не в начале, строка, начинающаяся с `---` или `...` не как маркер документа, табуляция в отступе и как разделитель (после `:`, `-`, `?`, внутри flow-коллекции), скаляр без кавычек, который js-yaml читает числом в другой записи (`1.10`, `010`, `1e3`, `-0`) или датой (`2027-01-13`), значение `True`/`FALSE` и булевы YAML 1.1 (`yes`, `no`, `on`, `off`, `y`, `n`), скаляр, начинающийся с `,` `]` `}`, ключ `True`/`~`, повтор ключа, комментарий внутри flow-коллекции. Булевы настройки (`excludeLinksFromLockfile`, `requiresBuild`, `ignoreScripts`, …) не `true`/`false` — отказ. Многострочная flow-коллекция разбирается за линейное время. Непрочитанный вход делает «не прочитанным» каждое правило.

## CLI

```bash
deps-guard check [--root DIR] [--base REF] [--format text|json|sarif|junit] [--out FILE] [--now ISO]
deps-guard baseline [--root DIR] [--out FILE]
deps-guard metadata [--root DIR] [--registry URL] [--out FILE] [--timeout-ms N]
```

`check --out` пишет отчёт выбранного формата в файл, а в журнал — текст. `--now` — дата ISO 8601 (`2026-11-16` или `2026-11-16T10:00:00Z`, с зоной); прочие записи (`1`, `Nov 15`) и время позже настоящего больше чем на сутки — отказ (будущее опорное время молча отключило бы свежесть). Опорное время печатается в каждом отчёте (`опорное время:` в тексте, `now` в JSON, `invocations[].properties.now` в SARIF). SARIF 2.1.0: «не проверено» — `kind: review`, не `pass`. JUnit: нарушение — `<failure>`, «не проверено» и «не прочитано» — `<error>`, отключённое правило — `<skipped>` с причиной.

`metadata` выгружает из реестра даты публикации ровно тех версий, что стоят в lock-файле, и признак install-скрипта, и сливает их с кэшем. Документ берётся из того реестра, откуда пакет ставится: `--registry`, иначе `registry` из `.npmrc` проекта, иначе `sources.defaultRegistry`; пакет scope — из `@scope:registry` `.npmrc`; архив по адресу — из реестра, которому принадлежит адрес (раскладка `<реестр>/<имя>/-/<файл>`; адрес вне раскладки и пакет из двух реестров — ошибка, а не данные одноимённого публичного пакета). Каждый запрос — с потолком (`--timeout-ms`, по умолчанию 15 с); пакет, который не удалось получить, в кэш не пишется, а называется в ошибках (код 2). Заголовок `Authorization` закрытого реестра — переменная `DEPS_GUARD_REGISTRY_AUTH`; он уходит только реестру по умолчанию, реестрам scope и хостам архивов — нет. Кэш коммитится: проверка в CI идёт без сети и воспроизводима.

Тексты отчёта, заголовки правил и сообщения CLI — на русском; идентификаторы правил, вердикты, коды выхода и структура JSON / SARIF / JUnit стабильны и от языка не зависят.

## CI

Гейт обязан отработать **до того, как выполнится хоть один install-скрипт**: npm и yarn исполняют скрипты при установке, и гейт после `npm ci` опоздал бы. Поэтому сам гейт ставится без скриптов (он их не имеет и в установке проекта не нуждается — читает файлы репозитория), а установка проекта со скриптами идёт следующим шагом (GitHub Actions):

```yaml
deps-guard:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v5
      with: { fetch-depth: 0 }
    - uses: actions/setup-node@v5
      with: { node-version: 24 }
    - run: npm install --no-save --ignore-scripts --prefix /tmp/deps-guard @hoshinotatsuya/deps-guard@<version>
    - run: /tmp/deps-guard/node_modules/.bin/deps-guard check --base "origin/${{ github.base_ref || 'main' }}" --format sarif --out deps-guard.sarif
```

Если гейт уже стоит в devDependencies, установка перед ним — только без скриптов (`pnpm install --frozen-lockfile --ignore-scripts`, `npm ci --ignore-scripts`, `yarn install --frozen-lockfile --ignore-scripts`). Вердикт от установки не зависит: установленный `node_modules` гейт не читает.

## Гейт в jest

```ts
// examples/deps-guard.spec.ts
import { join } from 'node:path';

import { depsGuardGate } from '@hoshinotatsuya/deps-guard/jest';

depsGuardGate({ root: join(__dirname, '..') });
```

`depsGuardGate(options)` — опции `check` плюс `title` (по умолчанию «deps-guard: цепочка поставок зависимостей»). Один `it` на правило; находки — в сообщении упавшего теста, «не проверено» — тоже красный тест. Отключённое правило — `it.skip` с причиной в имени.

## API

```ts
// examples/check.ts
import { writeFileSync } from 'node:fs';
import { join } from 'node:path';

import { DepsGuard, EXIT_CODE, type PackageMetadata } from '@hoshinotatsuya/deps-guard';

export function runGate(root: string): number {
  const report = DepsGuard.check({ root, baseRef: 'origin/main' });
  process.stdout.write(DepsGuard.render('text', report));
  writeFileSync(join(root, 'deps-guard.sarif'), DepsGuard.render('sarif', report));
  const code = DepsGuard.exitCode(report);
  if (code === EXIT_CODE.unverified) {
    // Nothing is violated, but something could not be checked: this is not green.
    const unverified = report.findings.filter((finding) => finding.verdict === 'unverified');
    console.error(`not verified: ${unverified.map((finding) => finding.subject).join(', ')}`);
  }
  return code; // 0 clean, 1 findings, 2 not verified
}

export async function refreshMetadata(root: string): Promise<Record<string, PackageMetadata>> {
  const lockfile = DepsGuard.readLockfile(root);
  const { metadata, errors } = await DepsGuard.fetchMetadata({
    registry: 'https://registry.npmjs.org/',
    packages: lockfile.packages,
    timeoutMs: 15_000,
  });
  if (errors.length > 0) {
    throw new Error(`metadata not fetched for ${errors.length} packages: ${errors.join('; ')}`);
  }
  return metadata;
}
```

| экспорт | что делает |
|---|---|
| `DepsGuard.check(options)` | все правила → `CheckReport` (`tool`, `root`, `lockfile`, `now`, `warnings`, `rules`, `findings`); на непрочитанном входе не бросает — это вердикт `broken` |
| `CheckOptions` | `root` (обязательно); `config` (вместо чтения `deps-guard.json`); `baseRef` (перекрывает базу из настройки); `metadata` (перекрывает кэш); `now` (по умолчанию — текущее время); `env` (по умолчанию `process.env`, выводятся только имена переменных `YARN_*`) |
| `DepsGuard.exitCode(report)` | 0 — чисто, 1 — нарушения, 2 — не проверено (`EXIT_CODE`) |
| `DepsGuard.render(format, report)` | `'text' \| 'json' \| 'sarif' \| 'junit'` |
| `DepsGuard.readLockfile(root, path?)` | разобранный lock-файл в общем виде (`Lockfile`); бросает `InputUnreadableError` |
| `DepsGuard.renderBaseline(root, lockfilePath?)` | текст файла базовой линии |
| `DepsGuard.fetchMetadata(options)` | `{ registry, scopeRegistries, packages, timeoutMs = 15_000, authorization, concurrency = 8 }` → `{ metadata, errors }` |
| `LoadConfig.fromRoot(root)`, `LoadConfig.validate(value)` | чтение / проверка `deps-guard.json` (`DepsGuardConfig`); неизвестный ключ и неверное значение — исключение |
| `RULE`, `RANGE_KINDS`, `MIN_REASON_LENGTH`, `EXIT_CODE` | замороженные константы |

Метаданные можно передать в `check` напрямую (`metadata`) — они перекрывают кэш.

## Форматы lock-файлов

- `pnpm-lock.yaml` версий 6.x и 9.x, в том числе несколько документов (pnpm 11+ пишет первым документ окружения — сам pnpm и config-зависимости; они тоже проверяются).
- `package-lock.json` / `npm-shrinkwrap.json` версий 2 и 3.
- `yarn.lock` версии 1, с workspaces (каталоги — по `workspaces` package.json: yarn 1 проекты в yarn.lock не пишет).
- `yarn.lock` yarn 2+ (berry), `__metadata.version` 4–10 (yarn 4.13 пишет 8, 4.14 — 9, 4.15+ — 10) — см. раздел «yarn 2+». Какой формат перед гейтом, решается как у самого yarn: заголовок `# yarn lockfile v1` в начале файла — yarn 1, иначе — YAML berry.
- Два lock-файла рядом без ключа `lockfile` — отказ: неизвестно, каким ставит CI.
- Проекты workspace — каталог, а не список из lock-файла: pnpm — `packages` в pnpm-workspace.yaml, npm и yarn — `workspaces` в package.json. Шаблоны: `*`, `?`, `**`, исключение `!шаблон`; прочий синтаксис glob (`{a,b}`, `[ab]`, `@(…)`), `\`, путь вне корня (`../x`, `/x`, `C:/x`) — отказ. `*` и `**` не заходят в скрытые каталоги, явный сегмент (`.tools/*`) — заходит, как у менеджеров; на диске скрытые каталоги обходятся (как в списке файлов git-ревизии базы). `node_modules` и `.git` не обходятся, у pnpm не судятся ещё `bower_components`, `test`, `tests` (так ищет проекты сам pnpm). Каталог-ссылка и каталог глубже 32 уровней, до которых дотягивается шаблон, — «не прочитано».

## yarn 2+ (berry)

Замер на настоящем yarn 4.0.2, 4.13.0, 4.14.0, 4.14.1, 4.15.0 и 4.18.1 (и разбор lock-файлов yarn 3.4.1) с изолированным пользовательским конфигом, поддельным реестром и git на 127.0.0.1; lock-файлы фикстур `fixtures/yarn-berry-project` записаны ими же (`formats/` — один проект со всеми протоколами, записанный 4.13.0, 4.14.1 и 4.18.1).

- **Форматы 8, 9, 10.** Записи одинаковы: тот же проект, записанный тремя версиями, отличается только `__metadata.version` (checksum `10c0/…`, `conditions`, `resolution` — как в формате 8). Меняются умолчания настроек, и формат — свидетельство поколения yarn: формат 9+ пишет yarn 4.14+, младший yarn в CI (там установка неизменяемая) такой файл не примет — переписал бы версию формата (замер: YN0028), а yarn 4.14+ на файле формата 8 сам дописывает в `.yarnrc.yml` прежние умолчания (`enableScripts: true`, `approvedGitRepositories: ["**"]`, у 4.15+ ещё `npmMinimalAgeGate: 0`) и в CI отказывает. `enableImmutableInstalls: false` это свидетельство снимает — тогда гейт судит, как формат 8.

- **Разбор.** yarn читает yarn.lock и `.yarnrc.yml` js-yaml со схемой FAILSAFE: каждый скаляр — строка как написан (`2.1`, `true`, `0b08…`), пустое значение — null, повтор ключа — последний. Гейт читает так же , но структура — то же строгое подмножество (табуляция-разделитель, якоря, повтор ключа — отказ). Сверка с js-yaml FAILSAFE: 7 настоящих yarn.lock (форматы 6 и 8, до 3 855 пакетов) и 7 `.yarnrc.yml` — совпадают.
- **Источник** — по протоколу локатора `resolution`: `npm:` — реестр установки; `patch:` — источник исходного пакета (встроенные `~builtin<compat/…>` и патчи из репозитория); `workspace:` — проект (его прямые зависимости yarn пишет одним списком, поле при сверке не сравнивается); `link:` — ссылка; `portal:` и `file:` — каталог или архив (путь — от проекта из привязки `locator=`); `exec:` — нераспознанный источник: yarn собирает пакет, исполняя скрипт, — до 4.14 при любой настройке скриптов, с 4.14 — только если скрипты разрешены (`enableScripts: true` или `built: true`; иначе установка отказывает; замер), поэтому это и нарушение `source` без допуска, и install-скрипт; git-зависимость yarn собирает `yarn pack`, исполняя её `prepack`, при любых `enableScripts` и `dependenciesMeta` (замер 4.0.2–4.18.1) — решение для неё только `installScripts.allow`; с 4.14 git ставится только из `approvedGitRepositories` (по умолчанию — ни один), гейт этого не заменяет: git без допуска — нарушение `source` всегда; адрес с `#commit=` — git; прочий http(s) — архив. Неизвестный протокол, версия формата вне 4–8, запись без `resolution` — «не прочитано».
- **checksum** — sha512 архива в кэше yarn: 128 hex, у yarn 4.1+ с префиксом `cacheKey/`. Префикс не текущего `__metadata.cacheKey` yarn не сверяет вовсе (замер: подменённый хэш с префиксом `9/` — установка прошла), поэтому такой checksum, обрезанный и отсутствующий — нарушение. Пакет платформы (`conditions: os=…`) yarn записывает без checksum и на подходящей платформе ставит без сверки — нарушение с подсказкой про `supportedArchitectures`. `checksumBehavior` в `.yarnrc.yml` не `throw` — нарушение.
- **Реестр установки** — `npmRegistryServer` и `npmScopes.<scope>.npmRegistryServer` в `.yarnrc.yml`; `.npmrc` и `.yarnrc` yarn 2+ не читает (замер `yarn config get`). Значение `${…}` — «не проверено».
- **Скрипты.** yarn до 4.14 (формат 8 и младше) по умолчанию выполняет install-скрипты всех пакетов; yarn 4.14+ (формат 9+) — ни одного (`enableScripts` по умолчанию `false`). Решение — `dependenciesMeta.<пакет[@версия]>.built` корневого package.json (`false` — запрещён, `true` — разрешён); `enableScripts: false` в `.yarnrc.yml` запрещает остальные, а `built: true` разрешает и при нём (замер). Булево — как приводит yarn: `true`/`1`, `false`/`0`; иное — «не прочитано». `ignore-scripts` в `.npmrc`/`.yarnrc` — «не читается этой версией».
- **Согласованность.** Диапазон package.json сверяется с записью проекта как есть и в форме дескриптора (`^1.0.0` → `npm:^1.0.0`). `catalog:[имя]` (yarn 4.10+) — по каталогу `.yarnrc.yml` (`catalog`, `catalogs.<имя>`, как у pnpm): пакет записан под дескриптором диапазона из каталога; записи в каталоге нет или дескриптора нет в lock-файле — висячая. Плавающий диапазон каталога судит `floating-range`, новую зависимость — по пакету из каталога (база — по `.yarnrc.yml` базы).
- **Не заменяет установку.** `npmMinimalAgeGate` (yarn 4.10+, умолчание `1d` с формата 10) и `npmPreapprovedPackages` действуют при установке; гейт их не читает — его порог `freshness` свой. Прямая зависимость без дескриптора в lock-файле — висячая, кроме подменённой `resolutions` корня на дескриптор, который в lock-файле есть (так yarn пишет `patch:` из `resolutions`).
- **Код и зависимости `.yarnrc.yml` — как прямые зависимости (`new-dependency`).** `yarnPath` и `plugins` — файлы из репозитория, которые исполняет ЛЮБАЯ команда yarn (замер на yarn 4.0.2 и 3.4.1; `checksum` записи плагина yarn 4.0.2 не сверяет): предмет — `yarnPath@<путь>#sha256=<хэш>` и `plugin@<путь>#sha256=<хэш>`, смена пути или содержимого относительно базы — новая зависимость, пока предмет не внесён в `newDependencies.allow` с причиной. Путь вне репозитория (в том числе ссылкой), нечитаемый файл, плагин без `path` (`spec` по адресу yarn не скачивает — замер), запись не по форме — «не прочитано». Зависимости `packageExtensions.<селектор>.dependencies` (yarn добавляет их чужому пакету; в yarn.lock они видны пакетами дерева и судятся остальными правилами, а у расширяемого пакета не записаны — замер) — предметы новой зависимости, как прямые. Файл базовой линии (`deps-guard baseline`) пишет и эти предметы.
- **Окружение.** Переменные `YARN_*` CI yarn берёт поверх `.yarnrc.yml`, а гейт окружения CI не видит. Если гейт запущен с такими переменными в собственном окружении (у проекта yarn 1 или 2+), в отчёте — строка `ПРЕДУПРЕЖДЕНИЕ` с их именами (значения не читаются: там бывают токены), в JSON — `warnings`, в SARIF — `toolExecutionNotifications`; код выхода не меняется.

## Чего пакет не делает и где граница

- **Признак install-скрипта** у pnpm lockfile v9 и yarn в самом файле не хранится. Источники: lock-файл (pnpm v6 `requiresBuild`, npm `hasInstallScript`), метаданные реестра, `package.json` локального каталога в репозитории. Установленный `node_modules` источником не служит: вердикт не зависит от того, ставили ли проект, а скрипт пакета мог переписать собственный package.json. Пакеты без данных — «не проверено»; полностью закрывает кэш `deps-guard metadata`.
- **Какие решения о скриптах читает менеджер** (замер на pnpm 9.15, 11.1, 12.4, 12.10.1, 12.11.0, 12.21.0, yarn 1.22 и yarn 2+ 4.0.2–4.18.1; pnpm 10 не замерен — для него читаются все источники разом):

  | менеджер | читает | не читает |
  |---|---|---|
  | npm | `ignore-scripts=true` в `.npmrc` | — |
  | yarn 1 | `ignore-scripts true` в `.yarnrc` (ключ можно в кавычках или с `--`) | `.npmrc` — yarn 1 выполняет postinstall при `ignore-scripts=true` там |
  | pnpm < 10 | поле `pnpm` package.json: `onlyBuiltDependencies`, `onlyBuiltDependenciesFile`, `neverBuiltDependencies`; `ignore-scripts` в `.npmrc` | настройки в pnpm-workspace.yaml, `allowBuilds`, `ignoredBuiltDependencies` |
  | pnpm 11+ | pnpm-workspace.yaml: `allowBuilds`, `dangerouslyAllowAllBuilds`, `ignoreScripts` | поле `pnpm` package.json, `.npmrc` (`ignore-scripts`, `dangerously-allow-all-builds`), `onlyBuiltDependencies`, `neverBuiltDependencies`, `ignoredBuiltDependencies`; `permissions` до 12.11 |
  | pnpm 12.11+ | ещё `permissions.<ключ>.build` (`true`/`false`; запись перекрывает `allowBuilds` того же ключа, строка — решения нет; замер 12.10.1, 12.11.0, 12.21.0). Версия — `packageManager` или нижняя граница `devEngines.packageManager` (`^12.11.0` — читается, `^12.0.0` — нет) | — |
  | yarn 2+ | `enableScripts` в `.yarnrc.yml`, без него — формат yarn.lock (9+ — запрет); `dependenciesMeta.<пакет>.built` | `.npmrc`, `.yarnrc` |

- **Метаданные реестра строже установки.** Реестр дописывает неявный `install: node-gyp rebuild` пакетам с `gypfile` (замер: `fsevents@2.3.3` в реестре со скриптом, в архиве — без него и без `binding.gyp`). npm такой скрипт выполнит, pnpm — нет. Гейт берёт строгий ответ: такому пакету нужно решение (`allowBuilds: { fsevents: false }`).
- **`.npmrc` и `.yarnrc`** читаются только в ключах `ignore-scripts`, `dangerously-allow-all-builds`, `registry` и `@scope:registry` и так, как их читает менеджер: `.npmrc` — формат ini (строки делит и CR, и LF; ключ и значение в кавычках — без кавычек; хвост после `;`/`#` — комментарий; ключ без `=` — `true`), `.yarnrc` — формат yarn 1 (`ключ значение`, в кавычках или с `--`). Нужный ключ, который менеджеры читают по-разному, — «не прочитано» со строкой: в `.npmrc` после заголовка секции `[…]` (npm, pnpm 9 и pnpm 11 его на верхнем уровне не видят — замер: postinstall выполняется; pnpm 12 берёт), с суффиксом `[]`; в `.yarnrc` — с отступом (вложенный) и не по формату. Остальные строки не разбираются и не выводятся (там токены; тест: значение токена не попадает ни в находки, ни в один формат отчёта); учётка в адресе реестра в находку не попадает. Реестр из `.npmrc` пользователя, глобального `.npmrc` и переменных окружения CI гейт не видит — его задаёт `sources.defaultRegistry`.
- **Протоколы** (`workspace:`, `file:`, `link:`, `git+…`) правило диапазонов не судит: источник — дело правила `source`. `catalog:` судится по каталогу pnpm-workspace.yaml.
- **Похожие имена** — эвристика по списку. Отбрасывание scope (`types-node` при популярном `@types/node`) не ловится: так устроены и законные пакеты (`pg-types`, `babel-core`). Имя внутри популярного scope (`@aws-sdk/client-sso` рядом с `client-s3`) не судится: scope в реестре принадлежит владельцу, публикует в него только он. Встроенный список — широко известные пакеты; для своей экосистемы его стоит заменить (`popularFile`).
- **Подтверждено замером на настоящих менеджерах** (изолированный пользовательский конфиг, поддельный реестр на 127.0.0.1): модель решений о скриптах (pnpm 9/10/11/12, yarn 1), `ignore-scripts` в секции ini у pnpm 9 не действует, реестр установки из `.npmrc` (pnpm 12) и из `.yarnrc` (yarn 1), разбор YAML — на 156 настоящих `pnpm-lock.yaml`/`pnpm-workspace.yaml`: с js-yaml совпадают все, с pnpm 12 — 52 файла настроек (`pnpm config list`) и 100 lock-файлов (дерево `pnpm list --lockfile-only`, 58 914 пакетов), плюс записанные ответы pnpm 12 на враждебные входы (`fixtures/yaml-oracle`, перезапись — `scripts/record-pnpm12-yaml.cjs`). **Не замерено**: npm-реестры с нестандартной раскладкой, пути Windows в lock-файле на самой Windows (машины с Windows не было; пути `C:\…` и `\\сервер\…` разбираются как абсолютные по правилам Windows, но на Windows не прогонялись).
- **Живой реестр гейт не опрашивает** — только команда `metadata`. Порог свежести pnpm (`minimumReleaseAge`) действует при установке и гейт не заменяет: гейт ловит свежую версию, попавшую в lock-файл до того, как порог включили, или поставленную другим менеджером.

## Поведение при отказе

Fail-closed везде: нет `deps-guard.json`, неизвестный ключ, пустой список популярных имён, неразобранный lock-файл или настройка, нет базовой ревизии — отказ (`broken`, код 2), а не молча прошедшее правило. Нет данных (даты публикации, признака install-скрипта, реестр известен только окружению CI) — `unverified` (код 2): это отличается и от успеха, и от нарушения. Нарушение побеждает всегда: есть нарушение или устаревший допуск — код 1.

## Совместимость

* Node.js ≥ 24.
* Менеджеры: npm (lock-файлы v2/v3; проверено на npm 12.2.2), yarn 1 (1.22.22), yarn 2+ (4.0.2–4.18.1, форматы 4–10), lock-файлы pnpm 6/9 (pnpm 9.15–12.21.0).
* Проекты потребителя: CommonJS (`node10`, без карты exports), `node16`, `nodenext`, ESM `nodenext` и `bundler`, везде `strict` + `exactOptionalPropertyTypes` и `skipLibCheck: false` (`pnpm run test:consumers`).
* jest ≥ 29 для `./jest`.

## Разработка и тесты

```bash
pnpm install
pnpm run typecheck        # src и examples/
pnpm run lint             # biome
pnpm test                 # сборка, затем jest последовательными группами не больше 300 тестов, 2 воркера
pnpm run test:consumers   # собранный пакет в одноразовых проектах + установленный CLI на настоящих lock-файлах
pnpm run build
```

Набору нужен только git (спеки базы и сквозной прогон CLI создают git-репозитории; поддельный реестр — на 127.0.0.1).

Матрица потребителей (`pnpm run test:consumers`, входит в `prepublishOnly`): собранный архив пакета ставится в пять одноразовых проектов — CommonJS (node10, без карты exports), node16, nodenext, ESM nodenext и ESM bundler, везде strict + exactOptionalPropertyTypes без skipLibCheck; входы берутся из карты `exports`; в каждом — tsc, загрузка входов в рантайме (вход `/jest` — разрешение пути: он грузится только в среде jest), ts-jest у CJS и запуск установленного CLI на маленьком проекте (чисто — код 0, новая зависимость — код 1); плюс установленный CLI на настоящих lock-файлах последних менеджеров (`fixtures/latest`: npm 12.2.2, yarn 1.22.22, pnpm 12.21.0; `fixtures/yarn-berry-project/formats`: yarn 4.13.0, 4.14.1, 4.18.1) — каждое правило прочитало вход.

Правила гоняются на фикстурах с разрешённым И запрещённым случаем; сквозные сценарии (`run-check-scenarios.spec.ts`) — синтетические проекты pnpm, npm и yarn на диске, по одному на каждый случай, где гейт отвечал не то; сквозной тест — собранный CLI во временном git-репозитории с настоящими lock-файлами pnpm 12 (база — коммит, рабочее дерево — новые зависимости: реестровая с плавающим диапазоном, два локальных каталога, один с `postinstall`), с поддельным реестром на 127.0.0.1 для `metadata`. Гейт jest проверяется вложенным jest: зелёный проект — все тесты прошли; нарушение — красный тест своего правила; отключённое — `skip` с причиной. Разборщик YAML сверяется с эталонным разборщиком YAML 1.2 и с js-yaml (им читает pnpm до 11) на настоящих lock-файлах, на формах сериализатора pnpm и на враждебных входах, и с записанными ответами pnpm 12 (`fixtures/yaml-oracle`): всё, что подмножество принимает, прочитано так же, как у каждого принявшего вход менеджера, а вход, который они читают по-разному, отвергнут.
